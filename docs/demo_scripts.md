## 1. 演示前准备清单

### 1.1 环境检查清单

| 检查项 | 状态 | 验证方法 |
|--------|:----:|---------|
| Dify 服务正常运行 | ☐ | 访问 http://localhost 可登录后台 |
| 知识库已索引完成 | ☐ | Dify 后台查看知识库状态为「已就绪」 |
| 后端服务正常运行 | ☐ | 访问 http://localhost:8000/health 返回 ok |
| 前端页面正常打开 | ☐ | 访问 http://localhost:5173 显示页面 |
| LLM API Key 有效 | ☐ | 后端日志无 API Key 错误 |
| 网络连接稳定 | ☐ | ping 测试无丢包 |

### 1.2 数据准备

| 准备项 | 说明 |
|--------|------|
| 测试用户 ID | `demo_student_001`、`demo_career_001`、`demo_office_001` |
| 清空历史数据 | 演示前清空 data/ 目录下的测试用户数据 |
| 备用截图/视频 | 准备演示各步骤的截图，以防万一 |

### 1.3 演示环境

- 推荐浏览器：Chrome / Edge 最新版
- 推荐分辨率：1920×1080 及以上
- 关闭不必要的浏览器插件（广告拦截等可能影响 SSE）
- 准备好屏幕共享（如远程演示）

### 1.4 人员分工（三人演示）

| 角色 | 负责 | 提示词 |
|------|------|--------|
| 主讲人 | 讲解产品理念、演示操作 | 控制节奏，讲解亮点 |

## 2. 演示脚本一：零基础学生

### 2.1 用户画像

| 维度 | 详情 |
|------|------|
| **背景** | 大一新生，计算机相关专业，之前完全没接触过编程 |
| **目标** | 入门 Python，为后续专业课程打基础 |
| **时间** | 每天 1 小时，持续 3 个月 |
| **偏好** | 喜欢视频教学 + 动手练习，不太能啃纯文字教材 |
| **痛点** | 不知道从哪里开始，网上教程太杂，容易半途而废 |

### 2.2 演示步骤

#### 第 1 步：打开页面（0:00 - 0:30）

**操作**：
- 打开浏览器，访问 http://localhost:5173
- 展示首页界面：左侧导航 + 右侧对话区

**讲解话术**：
> "大家好，欢迎来到 Ruyi Learning Planner 智能学习规划助手。今天我们要演示的第一个场景是：一位完全零基础的大学生，想系统学习 Python。我们来看看系统是如何帮助他的。"

#### 第 2 步：初始对话（0:30 - 2:00）

**操作**：
- 在输入框输入：`我想学Python，但是我完全零基础`
- 点击发送按钮

**预期效果**：
- 系统开始流式回复（打字机效果）
- 首先询问学习目标

**讲解话术**：
> "大家看，系统不会一上来就给你一个计划，而是先了解你的情况。就像一个真人学习顾问一样，它会引导式地提问，收集足够的信息后再生成计划。"

**用户继续输入（系统问什么答什么）**：

| 轮次 | 用户输入 |
|:----:|---------|
| 1 | 我想学Python，但是我完全零基础 |
| 2 | 目标是入门Python，为以后专业课打基础 |
| 3 | 我是纯小白，什么都不会 |
| 4 | 每天大概 1 小时，周一到周日都可以学 |
| 5 | 我比较喜欢视频 + 动手练习 |

#### 第 3 步：生成学习计划（2:00 - 4:00）

**操作**：
- 系统收集完信息后，自动开始生成计划
- 展示 SSE 流式输出的各个阶段

**预期效果**：
- 显示进度提示：「正在分析用户画像...」
- 显示知识库检索结果
- 显示前置依赖检查
- 显示计划评估
- 最终展示完整的学习计划

**讲解话术**：
> "好的，画像收集完成了。现在系统正在后台做几件事：
> 第一，检索我们的 Python 知识库，获取学习路径资料；
> 第二，检查前置依赖，确保学习路径的合理性；
> 第三，调用大模型生成个性化的学习计划；
> 第四，自动评估计划质量。
> 大家注意看，整个过程是流式的，你可以实时看到进度，而不是傻等。"

**SSE 事件流转**：

在生成计划的过程中，你会依次看到以下 SSE 事件：

| 顺序 | 事件类型 | 说明 |
|:----:|---------|------|
| 1 | `session_created` | 会话创建成功，生成唯一会话 ID |
| 2 | `token` | 流式输出 token，打字机效果逐字显示 |
| 3 | `profile` | 用户画像分析完成，输出结构化的用户画像 |
| 4 | `knowledge` | 知识库检索完成，返回相关学习资料 |
| 5 | `prerequisite` | 前置依赖检查完成，标记需跳过/需学习的内容 |
| 6 | `evaluation` | 计划质量自评估完成，给出打分和改进建议 |
| 7 | `schedule` | 学习日程生成完成，按天/周排列具体任务 |
| 8 | `plan` | 完整学习计划生成完毕 |
| 9 | `done` | 整个流程结束 |

> **讲解要点**：这 9 个事件体现了系统的多阶段处理能力，每一步都有实时反馈，而不是让用户等待。

#### 第 4 步：查看计划详情（4:00 - 6:00）

**操作**：
- 计划生成完成后，点击「查看完整计划」按钮
- 跳转到计划看板页面

**预期效果**：
- 展示里程碑卡片：共约 12 周，分 3-4 个阶段
- 每个里程碑有：阶段名称、学习目标、任务数量、难度
- 点击里程碑可展开查看每日任务
- 每日任务有：任务名称、预计时长、资源链接

**讲解话术**：
> "这就是生成的学习计划。我们来看，对于零基础的同学，计划从最基础的变量、数据类型开始，循序渐进，一共 12 周，正好 3 个月。
> 每个阶段都有明确的里程碑，每天的任务都精确到小时，完全匹配用户每天 1 小时的时间安排。
> 而且每个任务都附带学习资源链接，可以直接点击学习。"

**亮点展示点**：
- ✅ 12 周完整规划，正好 3 个月
- ✅ 从零基础开始，循序渐进
- ✅ 每天 1 小时，时间精准匹配
- ✅ 每个任务有预计时长和资源链接
- ✅ **流式响应**（打字机效果），边生成边看，不用傻等
- ✅ **多阶段进度反馈**，每一步都有对应事件，不是等半天出结果
- ✅ **计划质量自评估**（`evaluation` 事件），AI 自己给自己打分
- ✅ **前置依赖检查**（`prerequisite` 事件），确保学习路径合理
- ✅ **日历导出（ICS）**，一键导入手机日历，到点提醒

#### 第 5 步：今日任务页面（6:00 - 7:00）

**操作**：
- 点击左侧导航「今日任务」
- 展示今日待办任务列表

**预期效果**：
- 显示当天的学习任务
- 可勾选完成状态
- 显示进度统计：已学习天数、连续打卡、完成率

**讲解话术**：
> "在今日任务页面，用户可以清晰地看到今天该学什么，做完一个勾一个，非常有成就感。系统还会记录你的学习进度，连续打卡天数，帮你养成学习习惯。"

#### 第 6 步：反馈与调整（7:00 - 9:00）

**操作**：
- 回到对话页面
- 输入：`我觉得第2周的内容有点难，能不能放慢一点？`
- 发送

**预期效果**：
- 系统分析反馈
- 自动调整后续计划
- 显示调整前后的对比

**讲解话术**：
> "学习不是一成不变的。如果觉得难了、或者时间不够了，随时可以跟系统说。它会根据你的反馈动态调整计划。
> 大家看，调整后第 2 周的内容被拆分到了两周，难度降低了，更适合零基础的同学慢慢消化。"

**亮点展示点**：
- ✅ 自然语言反馈，不用填表
- ✅ 智能调整，自动平衡难度
- ✅ 调整前后对比，一目了然

## 5. 常见问题应急方案

### 5.1 技术类应急

| 问题场景 | 现象 | 应急方案 | 预防措施 |
|---------|------|---------|---------|
| **Hermes Agent 不可用** | 后端日志显示连接 Hermes 失败 | 1. 无需操作，系统自动降级到硅基流动 LLM<br>2. 如需演示 Hermes，可简单解释：「Hermes 是本地加速引擎，现在暂时用云端 LLM，效果一样」<br>3. 继续演示，功能完全不受影响 | 演示前确认 Hermes 服务已启动，准备好 LLM API Key 作为 fallback |
| **LLM API 超时/失败** | 对话卡住，长时间无响应 | 1. 安抚观众：「大模型偶尔会慢一点，我们稍等一下」<br>2. 刷新重试<br>3. 如持续失败，切换备用 API Key<br>4. 最坏情况：用预录的视频/截图继续讲解 | 演示前测试 API 可用性，准备备用 Key |
| **Dify 检索失败** | 知识库检索返回空 | 1. 不影响主流程，可跳过<br>2. 解释：「知识库检索是增强能力，不影响核心功能」<br>3. 继续演示计划生成 | 演示前确认知识库状态 |
| **前端页面白屏/报错** | 页面打不开或崩溃 | 1. 刷新页面<br>2. 清除浏览器缓存<br>3. 换浏览器重试<br>4. 重启 Vite 开发服务器 | 演示前充分测试，关闭干扰插件 |
| **SSE 流式中断** | 对话过程中断开 | 1. 重新发送消息<br>2. 解释是网络波动 | 使用有线网络，确保网络稳定 |
| **后端服务挂掉** | 所有请求失败 | 1. 快速重启后端服务<br>2. 同时用演示视频兜底 | 后端用稳定模式启动（不用 --reload） |
| **端口冲突** | 启动时报端口占用 | 1. 提前确认端口空闲<br>2. 修改端口重启 | 演示前一天完成全部部署验证 |

### 5.2 内容类应急

| 问题场景 | 现象 | 应急方案 |
|---------|------|---------|
| **生成的计划质量不理想** | 计划内容混乱、时间不合理 | 1. 主动承认：「大模型生成有时会有波动，我们可以让它重新生成一次」<br>2. 重新生成<br>3. 展示之前准备好的优质计划截图 | 提前测试 3 个场景各 3 次，确保稳定性 |
| **生成时间太长** | 观众等得不耐烦 | 1. 边等边讲解技术原理：「现在系统正在做知识库检索、前置检查、计划生成、质量评估这几步...」<br>2. 展示架构图，解释每一步在做什么 | 提前跑一遍，缓存结果（如果允许） |
| **答不上观众的技术问题** | 被问到不会的问题 | 1. 诚实回答：「这个问题很好，我们后续可以深入交流」<br>2. 把问题记下来，演示后解答 | 提前准备常见 Q&A 文档 |

### 5.3 演示节奏应急

| 问题场景 | 应对策略 |
|---------|---------|
| **时间不够** | 跳过次要环节，重点展示核心亮点：1. 个性化计划生成 2. 动态调整 3. 知识库问答 |
| **时间太多** | 深入展开：1. 展示代码架构 2. 演示更多调整场景 3. 现场让观众出题测试 |
| **观众注意力下降** | 增加互动：「大家觉得这个计划合理吗？」「有没有同学想现场试一下？」 |
